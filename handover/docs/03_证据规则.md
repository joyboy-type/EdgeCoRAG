# 三、证据规则（查询图 / GT 证据 / 检索候选的区分）

> 回应你「官方数据包含查询图 `image`、GT 图列表 `gt_images` 和 CLIP 候选图列表 `retrieved_images`，
> 三者需要区分」的要求。全部基于实测字段与官方源码行为。

---

## 1. 三个图片集合的严格定义

| 字段 | 类型（实测） | 语义 | 可否用于证据选择 | 可否用于评分 |
|---|---|---|---|---|
| `image` | 单张 RGB | **查询图**（问题所指的输入图像） | — 它是 query 的一部分 | 不参与评分 |
| `gt_images` | 5 张 × 1251 题；1 张 × 102 题 | **人工标注的正确证据** | ❌ **绝对不可** | ✅ 用于 GT 上界与命中判定 |
| `retrieved_images` | **恒 5 张** × 1353 题 | 官方 CLIP 风格检索候选 | ⚠️ 有条件下可用（见 §3） | ❌ 不参与评分 |

**已实测确认**：`retrieved_images` 恒为 5 张，1,353 题无一例外；
**官方未提供任何相似度分数**（无 `score`/`sim`/`rank` 字段）。

**query 图与 retrieved 的关系**：仅 **1 题**出现 query 图出现在 retrieved 中，
说明官方候选池基本是「与查询图相关但不同」的图，不是查询图自身。

---

## 2. 使用纪律（任务书硬性要求，建议写进我们的实验协议）

> **GT、正确答案和命中标记只用于评分、Oracle 条件和离线分析，
> 不能用于实际检索条件下的证据选择。**

具体落地为三条红线：

1. **`gt_images` 不得进入任何检索/选择/路由的输入**。
   任何"用 GT 反推该选哪张图"的逻辑都是 Oracle，只能标为**上界**，不得称为可部署方法。
2. **`answer_choice` / `answer` 不得参与证据选择**。
3. **命中标记（某候选是否为 GT）不得作为选择特征**，
   只能用于事后分析（例如「选中的证据是否为 GT」这个统计量本身）。

**我方的实现约束**（便于你审计）：
检索与选择模块的函数签名**不接收** `gt_images` / `answer_choice` / `answer`。
若将来需要做 Oracle 对照，会走**独立的 `oracle_*.py` 脚本**，并在产物里显式标注 `is_oracle=true`。

## 3. ⚠️ 官方候选池已部分泄漏答案（必读）

实测：**756 / 1353 = 55.9%** 的题目，其 `retrieved_images` 中**已包含至少 1 张 GT 正确证据**。

命中位置（0-based）：

| rank | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 命中题数 | **441** | 352 | 303 | 238 | 187 |

分场景命中率：Others 81.7% / Obstruction 73.1% / Scope 71.6% / Angle 70.2% /
Partial 54.5% / Temporal 44.3% / Biological 40.2% / Deformation 31.4% / **Incomplete 6.9%**

### 由此产生的证据规则

| 条件 | 池的构成 | 必须标注 | 能否用于主表结论 |
|---|---|---|---|
| **S1-a** `official_retrieved_top5` | 官方 `retrieved_images` 原样 | `pool_leakage_rate=0.559` | ⚠️ 只能作**与官方数字对照**，不能声称"检索能力" |
| **S1-b** `reindexed_corpus_v1` | 我方从官方 corpus 重检索 | `pool_leakage_rate=待测` | ✅ 干净基线 |
| **S2** `gt_evidence` | `gt_images` | `is_oracle=true` | ✅ 但只能作**上界** |
| **S3** `pure_distractor_v1` | **保证不含 GT** 的干扰图 | `contains_gt=false`（须逐题校验） | ✅ 干扰实验 |

**跨场景比较警告**：因为官方池的泄漏率在场景间从 6.9% 到 81.7% 相差 12 倍，
**用官方池做 S1 时，场景间对比是失真的**。分层分析请优先用 S1-b。

### 如何自查是否误含正确证据

不要靠肉眼。用**图片内容 sha256 精确比对**（我的实现见
`EdgeCoRAG-A/scripts/analyze_evidence_semantics.py`）：

```python
# 对候选图与 GT 图分别取原始字节 sha256，集合求交
gts = {sha256(img_bytes(g)) for g in item["gt_images"]}
rets = [sha256(img_bytes(r)) for r in item["retrieved_images"]]
hit_ranks = [i for i, s in enumerate(rets) if s in gts]
```

**注意**：不要用 `Image.save(PNG)` 再哈希来算指纹——对全量约 1.5 万张图重编码会慢到不可用
（实测全量扫描 >10 分钟未完成）。要直接对原始 JPEG 字节哈希。

## 4. ID—文件—内容哈希 对应关系（你要求的）

### 命名规范

```
原始题 ID   : item['id']                  → '0'、'42'（字符串，可能非数字）
项目内 qid  : f"mragb:{item['id']}"        → 'mragb:0'
evidence_id : f"{qid}#{role}{rank}"        → 'mragb:0#ret0'、'mragb:0#gt2'、'mragb:0#q'
文件名      : q_<raw_id>.png / gt_<raw_id>_<rank>.png / ret_<raw_id>_<rank>.png
```

`role` 取值：`q`（查询图）、`gt`（人工标注证据）、`official_retrieved`（官方候选）、
`reindexed`（我方重检索，**待定**）、`distractor`（S3 干扰图，**待定**）。

### `evidence_index.csv` 字段（已实现）

| 列 | 含义 |
|---|---|
| `evidence_id` | 稳定 ID，如 `mragb:0#ret0` |
| `raw_id` | **原始 `item['id']`，保留映射，不反解** |
| `qid` | 项目内 qid，如 `mragb:0` |
| `role` | 见上 |
| `rank` | 该角色内的顺序（0-based）；查询图为空 |
| `path` | 相对 `samples/` 或冻结包根目录的路径 |
| `sha256` | **图片内容哈希**（原始字节），用于跨版本校验与查重 |
| `w` / `h` | 原始像素宽高 |

**这些字段正是你要求的「ID—文件—内容哈希」对应关系。**
`sha256` 是跨版本复验的依据：只要 sha256 一致，就能确认是同一张图。

## 5. 顺序语义（容易出错的地方）

| 集合 | 顺序含义 | 是否承载信息 |
|---|---|---|
| `image_files`（送入模型） | **查询图固定在第 1 位**，其后按证据顺序 | ✅ 顺序是变量，必须记录 |
| `gt_images` 原始顺序 | 官方顺序，**无语义** | 否（仅作集合） |
| `retrieved_images` 原始顺序 | **官方检索排名（rank 0 最优）** | ✅ 是 |
| 我方 `reindexed` 顺序 | 我的检索排名 | ✅ 是 |

**建议**：送入模型的证据**统一按排名升序**排列，并在结果行里同时记录
`evidence_ids_order`（实际送入顺序）与 `retrieval_rank`（排名），
这样"顺序效应"和"选择效应"可以分开分析——这对你的错误分析有用。

## 6. 失败与缺失的处理（任务书要求）

任务书明确：**「检索失败、图片缺失等记录，失败题目不要直接删除。」**

规则：

1. 任何一题若图片缺失/损坏/下载失败，**保留在清单中**，把该行 `status` 置为
   `missing_image` / `corrupt_image` / `retrieval_failed`，**不得静默丢弃**。
2. 统计准确率时，**同时报告**「含失败题的全量分母」与「仅成功题的分母」两个数字。
3. 失败原因写入 `notes` 列。
