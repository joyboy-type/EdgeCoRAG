# 三、证据规则（查询图 / GT 证据 / 检索候选的区分）

> 本版按修订要求重写。**核心修正是术语**：先前使用的"答案泄漏"表述不成立，
> 现统一为「**GT 图像字节级精确匹配命中率**」。

---

## 1. 三个图片集合的严格定义

| 字段 | 类型（实测） | 语义 | 可否用于证据选择 | 可否用于评分 |
|---|---|---|---|---|
| `image` | 单张 RGB | **查询图** | — 它是 query 的一部分 | 不参与评分 |
| `gt_images` | 5 张 × 1251 题；1 张 × 102 题 | **人工标注的正确证据** | ❌ **绝对不可** | ✅ 用于 GT 上界与命中判定 |
| `retrieved_images` | **恒 5 张** × 1353 题 | 官方提供的检索候选 | ⚠️ 有条件下可用（见 §3） | ❌ 不参与评分 |

**已实测**：`retrieved_images` 恒为 5 张；**官方未提供任何相似度分数**
（无 `score`/`sim`/`rank` 字段）。

---

## 2. ⚠️ 术语更正：命中率 ≠ 答案泄漏

### 2.1 先前表述的问题

上一版我写了「候选池已部分泄漏答案（55.9%）」。**这个表述不成立**，原因有三：

1. **无法区分两类成因**：
   - (a) **正常检索命中**——检索器独立找到了正确证据，这是检索**成功**，不是缺陷；
   - (b) **利用答案/GT 标注生成候选**——这才是"泄漏"。
   仅凭"同一张图出现在两个集合里"**无法判定属于哪一类**。
2. **官方候选的产生过程未被完整公开**（详见 `official_pool_provenance.md`），
   我没有任何依据把观测到的重叠归因于 (b)。
3. **反向也不成立**：自研重检索**不能默认就是干净基线**。它的命中率必须同样实测、
   同样报告，其语料来源与许可也需单独确认。低命中率不等于干净。

### 2.2 现在的准确表述

| 指标 | 定义 | 实测值 |
|---|---|---|
| **GT 图像精确匹配命中率（任意）** | 题 q 的 `retrieved_images` 中，存在至少一张图的字节哈希等于 `gt_images` 中某张图 | **756/1353 = 55.9%** |
| **GT 图像精确匹配命中率（rank-0）** | `retrieved_images[0]` 即为某张 GT | **441/1353 = 32.6%** |
| **全部 GT 被覆盖的比例** | `gt_images` 的**全部**图都出现在候选中 | **31/1353 = 2.3%** |

**可复现要素（按要求附上）**：

| 项 | 值 |
|---|---|
| 计算脚本 | `a-side/scripts/audit_gt_match_rate.py` |
| 数据版本 | `uclanlp/MRAG-Bench` @ `43620fde4044bb150e158c67ad7af6b6b11e1da2` |
| split | `test` |
| **分母** | `questions_with_nonempty_gt` = **1353**（与全部题数相同，已在输出中声明） |
| 哈希口径 | sha256(JPEG quality=95 重编码字节) |
| 输出记录 | `a-side/data/gt_match_rate_audit.json` |
| 复算命令 | `python scripts/audit_gt_match_rate.py` |

### 2.3 哈希口径的说明（重要，先前有错）

实测发现：数据集流式加载得到的 `PIL.JpegImageFile` 的
`im.fp` / `_data` / `data` / `filename` **全部为 None**，**原始字节取不到**。
因此任何"取原始字节"的实现实际都会落到**重编码**分支。

- 重编码是**确定性**的：同一张图在多次独立加载中，JPEG95 与 PNG 两种口径的哈希
  各自完全一致（`scripts/test_hash_stability.py` 验证 3 次独立加载）。
- 用重编码哈希做**集合匹配**是有效的：GT 与候选使用同一口径，匹配关系是双射，
  **命中率不受容器格式选择影响**（JPEG95 与 PNG 两口径均已核对，结果同为 55.9%）。
- 但**交付的图片文件是重编码产物，不是原始字节**。这一点已在
  `samples/sample_meta.json` 的 `encoding` 字段中显式声明。

### 2.4 分场景命中率（差异达 12 倍）

| scenario | 题数 | 任意命中 | 命中率 | rank-0 命中率 |
|---|---|---|---|---|
| Others | 120 | 98 | **81.7%** | 51.7% |
| Obstruction | 108 | 79 | 73.2% | 54.6% |
| Scope | 102 | 73 | 71.6% | 43.1% |
| Angle | 322 | 226 | 70.2% | 39.1% |
| Partial | 246 | 134 | 54.5% | 30.9% |
| Temporal | 149 | 66 | 44.3% | 22.1% |
| Biological | 102 | 41 | 40.2% | 21.6% |
| Deformation | 102 | 32 | 31.4% | 16.7% |
| **Incomplete** | 102 | 7 | **6.9%** | 2.0% |

### 2.5 这个数字**能**支持什么、**不能**支持什么

**能支持（作为观测事实）**：

- 若把官方候选当 S1，则**在 55.9% 的题目上，S1 的证据集合里已经包含至少一张 GT 图**。
  这使 S1 与 S2（GT 条件）在**证据集合层面部分重合**，两者的性能差距会被结构性压缩。
- 该重合率在场景间相差 12 倍，所以**用官方候选做场景间对比时，差异里混着命中率差异**。

**不能支持**：

- ❌ 不能说官方候选"作弊"或"泄漏"——无法区分正常检索命中与使用标注生成。
- ❌ 不能反推官方检索器的质量（命中率高既可能是检索器强，也可能是池子构成所致）。
- ❌ 不能据此认定自研重检索是干净基线。

**因此的可操作结论**：这四个数字应作为**实验条件的描述性统计**随结果一起报告
（"本条件所用证据池的 GT 精确匹配命中率为 X"），而不是当作对数据集的指控。

## 4. 近重复检查（S3 的必要补充）

精确哈希不重叠**只证明没有相同字节**，**不能保证**没有近重复图或其它有效证据。

### 4.1 方法

用 **dHash（64 位感知哈希）** 度量视觉近重复，汉明距离分档：

| 汉明距离 | 分档 | 处置 |
|---|---|---|
| 0 | `identical_bits` | 视为同图 |
| 1–2 | `very_likely_same` | 视为同图（重编码/微调） |
| 3–6 | `near_duplicate` | **必须人工抽查** |
| 7–9 | `weak_similarity` | 记录，倾向通过 |
| ≥10 | `distinct` | 通过 |

### 4.2 已完成的检查

| 对象 | 结果 |
|---|---|
| 样例包内部（6 题，同一题内 GT/候选/查询图两两比对） | ✅ **无 hamming ≤ 6 的近重复对** |

脚本：`a-side/scripts/near_duplicate_check.py`；输出：`near_duplicate_report.json`。

### 4.3 ⚠️ 方法的局限（必须随结论一起报告）

1. **dHash 只度量视觉相似，不能判定语义是否支持答案**。
   这是本检查**最关键的局限**：
   - 官方池与 GT 的**同类不同实例图**（例如同为犬类但品种不同）**不会**被
     dHash 判为近重复，却**恰恰是最有威胁的干扰源**（外观相似但对象不符）；
   - 因此"无近重复"**不能**推导为"无支持信息"。
2. dHash 对旋转、大幅裁剪、水平翻转**不敏感**，会漏检。
3. 阈值 1–6 是经验值，**需人工抽查确认**，不得直接当结论。
4. 只能检"视觉近重复"，无法检"语义等价但外观不同"的图。

### 4.4 无法确定时的标记规则

**不得默认通过**。对每个 S3 干扰候选，需给出三态标记：

| 标记 | 含义 | 处置 |
|---|---|---|
| `verified_unsupportive` | 已人工确认不支持答案 | 可用 |
| `verified_near_duplicate` | 已确认近重复/同图 | **剔除** |
| `undetermined` | dHash 通过但**未做语义抽查**，或抽查无法判定 | **计入报告，不计入"已确认干净"** |

S3 交付物中必须给出三个计数：`verified_unsupportive` / `verified_near_duplicate` /
`undetermined`。**"纯干扰"集只有在 `undetermined = 0` 时才能声称已确认**。

## 5. 使用纪律（任务书硬性要求）

> **GT、正确答案和命中标记只用于评分、Oracle 条件和离线分析，
> 不能用于实际检索条件下的证据选择。**

三条红线：

1. `gt_images` **不得进入**任何检索/选择/路由的输入。
   任何"用 GT 反推该选哪张图"的逻辑都是 Oracle，只能标为**上界**。
2. `answer_choice` / `answer` **不得参与**证据选择。
3. **命中标记不得作为选择特征**，只能用于事后分析。

**实现约束**：检索与选择模块的函数签名**不接收** `gt_images` / `answer_choice` / `answer`。
Oracle 对照走独立脚本并在产物中标注 `is_oracle=true`。

## 6. ID—文件—内容哈希 对应关系

### 命名规范

```
原始题 ID   : item['id']                  → '0'、'42'（字符串，可能非数字）
项目内 qid  : f"mragb:{item['id']}"        → 'mragb:0'
evidence_id : f"{qid}#{role}{rank}"        → 'mragb:0#official_retrieved0'
文件名      : images/<raw_id>/<role>_<raw_id>_<rank>.jpg
```

`role` 取值：`q` / `gt` / `official_retrieved` / `reindexed` / `distractor`。

> **路径根目录**：所有 `path` 均相对 **`handover/samples/`**（见 §8）。
> 按 `raw_id` 分目录，是为将来把 S3 干扰图（取自别题）并入同一目录树时避免同名覆盖。

### `evidence_index.csv` 字段

| 列 | 含义 |
|---|---|
| `evidence_id` | 稳定 ID |
| `raw_id` | **原始 `item['id']`，保留映射，不反解** |
| `qid` | 项目内 qid |
| `role` | 见上 |
| `rank` | 该角色内 0-based 顺序 |
| `path` | 相对 `samples/` 的路径 |
| `sha256` | **落盘字节**的哈希（与文件内容一致，已验证） |
| `w` / `h` | 原始像素 |

**索引可能包含 `used_in_prompt=false` 的条目**（Incomplete 截断候选），
其来源在 JSONL 的 `available_evidence_untruncated` 中声明，**不留孤儿条目**
（已由 `verify_handover_sample.py` 校验）。

## 7. 顺序语义

| 集合 | 顺序含义 | 承载信息 |
|---|---|---|
| `image_files`（送入模型） | 查询图固定第 1 位，其后按证据顺序 | ✅ 顺序是变量 |
| `gt_images` 原始顺序 | 官方顺序，**无语义** | 否 |
| `retrieved_images` 原始顺序 | **官方排名（rank 0 最优）** | ✅ |

建议：送入模型的证据**统一按排名升序**，并在结果行同时记录
`evidence_ids_order`（实际送入顺序）与 `retrieval_rank`（排名），
使"顺序效应"与"选择效应"可分。

## 8. 失败与缺失的处理

1. 图片缺失/损坏/检索失败时，**保留在清单中**，`status` 置为
   `missing_image` / `corrupt_image` / `retrieval_failed`，**不得静默丢弃**。
2. **主准确率使用固定题单分母**（frozen 题单的全量），
   **成功子集指标仅作补充**，并**明确覆盖率**（成功题数 / 题单总数）。
3. 失败原因写入 `notes`。

> 这条与 B 侧的约定一致：主指标分母 = 固定题单，不随失败而变。
