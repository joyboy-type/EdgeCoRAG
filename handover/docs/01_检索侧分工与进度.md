### 2.1 体积口径差异已核清（要求一之5）

先前出现过 8 GiB 与 4 GiB 并存的混乱。实测各口径如下：

| 口径 | 值 | 量的是什么 |
|---|---|---|
| **A. 本地 parquet 实际字节** | **4.00 GiB** | 传输/计费口径 —— **与 B 报告的 ~4 GiB 一致** |
| B. 官方 API `usedStorage` | ≈ 8.0 GiB | 官方仓库侧计费口径（含远端副本/xet 分块，与本地快照不同） |
| C. 数据集卡 split `num_bytes` | ≈ 4.41 GiB | 数据集卡声明的解压前字节 |
| D. 解码后像素字节（`w*h*3`） | ≈ **42.8 GiB**（300 题外推 1353 题） | **模型实际要处理的计算口径** |

**结论：8 GiB 与 4 GiB 不矛盾，是不同口径。** 后续比较体积数字必须声明口径。
复算脚本：`a-side/scripts/reconcile_dataset_size.py`，输出 `size_reconciliation.json`。

> 注：官方 API 的 12 月 2024 元数据里 `usedStorage=8,576,331,248`（≈7.99 GiB），
> 而本地快照只有 28 个 `data/test-*.parquet` 共 4.00 GiB。
> 二者差异主要来自官方仓库侧对同一份数据的重复/分块计数，**不影响我们本地使用**。

## 3. 官方候选 vs 独立语料重检索（修订）

### 3.1 官方候选路线的**准确描述**

实测：官方候选中存在与 GT 字节相同的图 —— 任意命中率 **55.9%**、rank-0 **32.6%**、
全部 GT 被覆盖 **2.3%**。

**准确表述**：这是「**GT 图像字节级精确匹配命中率**」，
**不等于**「答案泄漏」。

**为什么不能称之为泄漏**：

1. 无法区分 (a) **正常检索命中**（检索器独立找到正确证据，这是检索成功）
   与 (b) **候选生成使用 GT/答案标注**；
2. 官方候选的**产生过程未被完整说明**（检索器、语料、query 形式均未公开）；
3. 观测形态**更符合** (a)：命中数分布递减（`0:597, 1:327, 2:208, 3:143, 4:54, 5:24`）、
   rank-0 命中占多数（441/756）、**全部 GT 覆盖仅 2.3%** —— 人为注入 GT 通常不会如此。

**但它确实影响实验设计**（这是我们能说的）：

- 若把官方候选当 S1，则**在 55.9% 的题目上 S1 的证据集合已含至少一张 GT 图**，
  使 S1 与 S2 在证据集合层面**部分重合**，两者差距被结构性压缩；
- 该重合率场景间相差 12 倍（6.9%–81.7%），故**场景间对比会混入命中率差异**。

### 3.2 反向警示：**自研重检索不能默认干净**

| 误解 | 事实 |
|---|---|
| "自己检索一遍就是干净基线" | ❌ 若使用**同一份官方语料**且 GT 图在语料中，命中率**仍会很高** |
| "命中率低就说明干净" | ❌ 命中率低也可能只是**检索器弱** |

**对自研重检索的要求**：同样实测并报告命中率；报告语料来源/版本/去重/许可；
**不得声称"干净基线"**，只能说"命中率为 X 的另一个池"。

### 3.3 两条路线的记录方式

| 路线 | `pool_id` | 用途 |
|---|---|---|
| A. 官方候选 | `official_retrieved_top5` | 与官方数字可比；**必须附命中率** |
| B. 独立重检索 | `reindexed_corpus_v1` | 另一条件；**同样附命中率与语料信息** |

**两条都做，分开成表，绝不混表。**

### ⚠️ 图片尺寸与 top-k 的硬约束

官方 RAG 提示模板的**图片占位符数量是写死的**（`dataloader.py:46,48`）：
常规 **6**（查询图+5 证据）、Incomplete **2**（查询图+1）。

→ 官方**只支持 5 张证据**。改 top-k **必须同步改占位符数量**，
改了**就不再与官方数字可比**，且必须另立 `protocol_version`。

**提议（待 B 确认）**：

| 项 | 提议 |
|---|---|
| 图片顺序 | 查询图固定第 1 位，证据按检索排名升序 |
| 尺寸 | **不预缩放**，交给各模型 `image_processor`；记录原始像素 |
| 数量 | S1 用 5 张（与官方一致）；另做 3 张对照，`proto_fixedk3_v1`，**分表** |

## 6. `Incomplete` 规则的意见（修订）

### 官方实际行为

```python
# eval/utils/dataloader.py
if scenario == 'Incomplete':          # 第 37-38 行: GT 只取首张
    gt_images = [gt_images[0]]
...
if scenario == 'Incomplete':          # 第 59-60 行: 候选只取首张
    retrieved_images = [retrieved_images[0]]
prompt = ... + placeholder * 6        # 第 46 行: 常规 6 个占位符
if scenario == 'Incomplete':          # 第 48 行: Incomplete 2 个
    prompt = ... + placeholder * 2
```

**实测验证**：`len(gt_images)==1` 的题数 = `Incomplete` 题数 = **102，完全重合、0 例外**。
→ 官方在**数据层面**已裁好，loader 里的判断是冗余保险。

### A 侧意见（**已按你要求的四点修正**）

1. **保留官方场景规则作为默认协议**（`proto_official_v1`：Incomplete=1、其余=5），
   与官方数字可比。
2. **固定 top-3 另立 `proto_fixedk3_v1`**，且**必须同步改占位符数量**，
   **不得与 v1 混表**。
3. **Incomplete 必须单独报告**——它的命中率只有 6.9%（其它场景 31%–82%），
   混入总分会把"检索带来的伤害"稀释掉。
4. ⚠️ **但不得从总体中剔除 Incomplete**。
   完整基准总体指标（9 个场景合并）**必须保留并作为主指标**；
   Incomplete 单独报告是**附加**，不是替代。

**主指标口径**：
- **主指标** = 全部 1,353 题（或冻结题单全量）的总体准确率，**使用固定题单分母**；
- **分场景** = 9 个场景各自的准确率，**Incomplete 单列**；
- **成功子集** = 仅作补充，且**必须给出覆盖率**。

### 需 B 确认

S1 主表中 Incomplete 是否也只用 1 张证据？
- 用 1 张 → 与官方协议一致，但该场景候选池更小；
- 用 5 张 → 与其它场景对齐，但偏离官方协议。
**我倾向**：主表用官方协议（Incomplete=1），另附 Incomplete=5 的敏感性分析。
