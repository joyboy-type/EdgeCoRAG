### 题 ID 约定（回应你的核验）

你核验得对：HF 原生字段是字符串 `id`（实测第一条为 `'0'`），**没有原生 `qid`，也没有 `evidence_id`**。

约定：

```
原始 ID      : item['id']           字符串，如 '0'、'42'
项目内 qid   : 'mragb:' + item['id']   前缀化，避免与其它数据集撞名
evidence_id  : f"{qid}#{role}{rank}"   例: 'mragb:0#ret0'、'mragb:0#gt2'
```

**保留映射**：`evidence_index.csv` 里 `qid` 列同时存 `'mragb:0'` 与原始 `'0'` 的对应，
不用猜、不用反解。**绝不用 Viewer 临时图片地址当稳定 ID**（同意你的判断）。

## 3. 先使用官方内置 CLIP top-5 候选图，还是独立语料重检索？

### ⚠️ 实测发现：官方候选池已经部分泄漏了答案

我对全量 1,353 题逐题比对了 `retrieved_images` 与 `gt_images` 的**图片内容 sha256**：

| 指标 | 实测值 |
|---|---|
| **至少命中 1 张 GT 的题数** | **756 / 1353 = 55.9%** |
| 命中位置（0-based rank） | rank0: **441**、rank1: 352、rank2: 303、rank3: 238、rank4: 187 |

分场景命中率（差异极大，直接影响你的分层分析）：

| scenario | 题数 | 命中题数 | 命中率 |
|---|---|---|---|
| Others | 120 | 98 | **81.7%** |
| Obstruction | 108 | 79 | 73.1% |
| Scope | 102 | 73 | 71.6% |
| Angle | 322 | 226 | 70.2% |
| Partial | 246 | 134 | 54.5% |
| Temporal | 149 | 66 | 44.3% |
| Biological | 102 | 41 | 40.2% |
| Deformation | 102 | 32 | **31.4%** |
| **Incomplete** | 102 | 7 | **6.9%** |

**这意味着什么**（对你的公平比较至关重要）：

1. 若把官方 `retrieved_images` 当作 S1（检索证据），
   **56% 的题目里正确证据本来就已在池中**——你测到的不是"检索系统的能力"，
   而是"模型能否从已含答案的池中挑出答案"。**不同场景之间不可比**（6.9% vs 81.7%）。
2. 因此**官方候选路线必须标注为 `leaky_official_pool`**，不能与独立重检索路线混在一张表里。
3. **反过来，这对 S3 是好事**：因为我们**确切知道哪些图是 GT**，
   所以能构造出**保证不含正确证据**的纯干扰集（见 `04_S3干扰证据规范.md`）。

## 4. 检索器、选择策略、top-k、图片尺寸与预处理

> 这一节大部分是**待定**，因为需要先取回 corpus 并跑通检索才能定。
> 下面明确区分「已定」与「待定」。

### 已定

| 项 | 决定 | 依据 |
|---|---|---|
| 检索器 | **EmbeddingGemma 2**（`google/embeddinggemma-2`） | 任务书指定；已实测可用 |
| 精度 | **BF16**（CUDA 支持）；不用 FP16 | 任务书精度规则 + 模型卡 |
| query 前缀 | `task: search result \| query: ` | 任务书：文本 query 加前缀，**图像不加** |
| 音频 | `config_kwargs={"audio_config": None}` 禁用 | 任务书 |
| 嵌入维度 | 768 主用，**128/256/512 做截断对照** | 任务书 A-P0-2 要求 |
| 截断后处理 | **必须重新归一化**，查询与库同维度 | 任务书硬性要求 |
| 图片转 RGB | 一律 `.convert("RGB")` 后处理 | 与官方 loader 一致 |

### 待定（取回 corpus 后定）

| 项 | 待定原因 |
|---|---|
| 语料索引范围与去重规则 | 需先看 corpus 实际结构 |
| top-k | 官方候选恒为 5；我们的 k 需要消融（1/3/5） |
| 选择策略 | 候选：cosine 相似度 / utility 打分（论文式 6）/ random / GT 上界 |
| 图片尺寸与重采样 | **需与你一起定**，见下 |

### ⚠️ 图片尺寸必须统一（这是公平比较的前提）

**关键约束（我实测官方代码得到）**：官方 RAG 提示模板里的图片占位符数量是**写死的**：

```python
# third_party/MRAG-Bench/eval/utils/dataloader.py:46
prompt = f"... {image_placeholder}" * 6   # 常规场景: 查询图 + 5 张证据
# 第 48 行: Incomplete 场景改成 2 个占位符
```

→ 官方**只支持 5 张证据**（以及 Incomplete 的 1 张）。
**如果你要用 top-3，提示模板必须改，而改了就不再与官方数字可比。**

建议我们统一（**请你确认**）：

| 项 | 提议 |
|---|---|
| 图片顺序 | 固定「查询图在前，证据按检索排名升序在后」，**顺序本身作为变量记录** |
| 尺寸 | **按各模型自身的 `image_processor` 处理**，不预缩放（避免双重缩放）；在结果里记录 `input_image_count` 与原始像素 |
| 数量 | S1 统一 **5 张**（与官方一致）+ 另做 **3 张** 对照，两者分开报告 |

## 6. 关于 `Incomplete` 规则的意见（你点名要的）

### 官方实际行为（我读了源码，比"只取首张"更细）

`third_party/MRAG-Bench/eval/utils/dataloader.py`：

```python
# 第 37-38 行: GT 分支
if scenario == 'Incomplete':
    gt_images = [gt_images[0]]

# 第 59-60 行: 检索分支
if scenario == 'Incomplete':
    retrieved_images = [retrieved_images[0]]

# 第 46-48 行: 提示模板
prompt = f"...{image_placeholder}" * 6        # 常规
if scenario == 'Incomplete':
    prompt = f"...{image_placeholder}" * 2    # Incomplete: 查询图 + 1 张证据
```

**并且我已实测验证**：`len(gt_images)==1` 的题数是 **102**，
`scenario=='Incomplete'` 的题数也是 **102**，**两者完全重合（0 例外）**。
→ 官方在**数据层面**就已经把 Incomplete 的 GT 裁成 1 张，loader 里的代码是**冗余保险**。

### 我的意见

**同意你的方案，但建议补充三点**：

1. **保留官方场景规则作为默认协议**（Incomplete 用 1 张，其余用 5 张），
   这样与官方数字可比。协议版本记为 `proto_official_v1`。

2. **但要注意 Incomplete 的语义特殊性**：这一场景的题目是**故意信息不完整**的
   （`gt_images` 只有 1 张），而且官方候选池对它的命中率只有 **6.9%**
   （其它场景 31%–82%）。所以：
   - Incomplete 上"检索证据几乎总是错的"，**它天然就是一个 S3 干扰场景**；
   - 分析时**必须单独报告 Incomplete**，不能混进总体准确率，
     否则「检索带来的伤害」会被其它场景稀释。

3. **另做固定 top-3 时，请务必同时改提示模板占位符数量**，
   并把协议版本单独记为 `proto_fixedk3_v1`。**不要复用 `proto_official_v1` 的名字**——
   否则两个不同协议的结果会被误当成同一条件。

### 一个需要你确认的点

官方 `retrieved_images` 恒为 **5 张**（1,353 题全部如此），
而 `gt_images` 有 5 张 / 1 张两种。所以：

- 做 **S1（统一检索证据）** 时，Incomplete 是否也只用 1 张？
  - 若用 1 张 → 与官方协议一致，但 Incomplete 的候选池会更小
  - 若用 5 张 → 与其它场景对齐，但偏离官方协议
- **我倾向**：S1 主表用官方协议（Incomplete=1），另附一版 Incomplete=5 的敏感性分析。

## 7. 关于第六部分（端到端性能测量）

我可提供的内容边界，**请按此理解，不要直接拼成实测端到端性能**：

| 我能给 | 我不能给 |

- **索引构建时间不得混为查询在线时间**；
- 每题记录：模型 revision、量化精度、框架版本、输入图像数量/像素、top-k、提示模板版本、任务切片。
