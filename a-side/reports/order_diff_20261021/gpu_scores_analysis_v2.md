# GPU 分数表：raw→q95 映射后求交（修正版 v2）

## 0. 撤回上一版结论

上一版"两侧 sha256 交集=0 → 无被交换两行"是**错的**：它把 history 的**归档原始字节 sha** 直接与 live 的 **q95 字节 sha** 求交，字节基线不同导致假 0。
更正：history 的 `sha256` 经 B 的键表 `pixel_identity_18955_keys.csv`（`sha256_raw → sha256_q95`）映射后，与 live 的 `sha256`（q95）求交。

键表 sha256：`7d51cf8e6b18e038cf7eeac0a88bf1cd8114a56af0fe529e8b687079fcdd4208`（18,955 行，经 GitHub API 取，rc=0）。

**要点**：
- **1049**：7 张重合且顺序完全一致 → 在"映射后重合子集"上**没有**换位，不支持"1049 有相邻交换"。
- **1051**：6 张重合，`c792`(hist8) 插到了 `9902`(hist9)/`76b5`(hist10) 之前，而 live 里 `9902`(4)/`76b5`(5) 在 `c792`(6) 之前 → **2 对换位**。
- **10**：3 张重合，`df5c`(live2) 与 `3ed5`(live3) 在 history 里顺序相反 → 1 对换位。
- **1062**：**仅 1 张重合**，不能当"相邻交换"例证。

换位对的两侧 rank 与分数见 `cross_pool_mapped.json` 的 `per_qid.*.common_q95_with_ranks`（含 live_score / hist_score）。

## 3. 修正后的结论句

> **五题中，1049/1051 在映射后重合 7/6 张；其中 1049 顺序完全一致、1051 存在 2 对相邻换位；**
> **1062 仅重合 1 张，不足以支持换位判定。整体不能归因于数值栈（缺少同池同 dtype 对照）。**

（"集合完全不变"的表述**撤回**；"三题中 0 题归因数值栈"的上一版结论作废，因为它是基于错误的字节基线求交。）

## 4. 仍然需要 B 的同池 fp32 表

映射求交只能告诉你"哪些候选重合、重合子集上顺序是否变"，**不能**证明换位是由数值栈造成的——
因为 live 是 fp32/4712、history 是 bf16/18955，dtype 与池两个变量同时变。
要真正归因数值栈，仍需 B 的**同 4,712 池、fp32、只变一个变量**的复现表（`pool_id=sha256:12f1e2fe…`、`dtype=float32`）。这一步不变。
