## 2. 任务 1 的核心结论（一句话版）

**"批大小"与"浮点误差"都不是已证原因，我不这样写。**
- 同配置重复编码**逐位一致**；numpy 逐题↔整批 GEMM↔分块 32↔torch float32 之间**改序 0 条**，最大分数差 7.7e-7。
- 查询批大小 16→1 只让 **15.5%** 的题改序（签名率 10.6%），对 5 题出现 ≥3 题的概率约 **1.0%**，且只中了 `1117`，与实测的 `1049/1051/1062` 不重合。
- 真正能到 1e-2 量级的是**口径**：归一化位置（bf16 内 vs float32 重归一化，改序 76.2%、改集合 23.4%）、编码 dtype（bf16 vs fp32，改序 78.5%）、解码路径（原始字节 vs q95，5 题里 2 题改序、1 题连 top3 都变）。
- 排序脆弱性普遍：1033 题里 **83.3%** 的 top10 最小相邻分差 < 1e-3。
- 对下游：那 3 题的 cosine top3 与 top10 集合未变 → **cosine 选图不受影响**；**utility 选图受不受影响本轮未测**（需要 E2B 前向），不能宣称无影响。

## 9. P0 更正与修复：清单行尾口径（2026-10-20 追加）

**我做错的地方**：§8 写的"36 个产物哈希全部未变 / a17 0 失败"是在 **Windows CRLF 工作树**上得出的。
`artifacts.json` 记录的是磁盘上的 CRLF 字节，而 git 提交与干净检出是 LF，
于是 B 在 `89ddb29` 的干净检出上跑 `a17` 得到 **rc=1、fail_count=72**（36 个文件各 sha + size 两条），
差值恰好 `rows+1` 字节/文件。**产物内容没有损坏，但清单在任何干净检出上都不可复算**——这是真实缺陷，上一轮的表述不成立。

**本轮修复（只动清单/属性/校验脚本，不动产物内容）**：

| 改动 | 内容 |
|---|---|
| `.gitattributes` | 新增 `a-side/retrieval_if_v1/** text eol=lf`，提交与检出统一 LF |
| `artifacts.json` | 按 **LF 字节**重算 36 个 sha256/bytes；`summary.hash_normalization = "LF"` + `line_endings` 统计 |
| `a17_verify_interface.py` | 比对前做 `\r\n→\n` 归一化；新增 `--strict-lf`（遇 CRLF 直接失败并给修复提示）；新增 `--iface`（测试用）；缺 `hash_normalization` 标记即失败 |
| `a23_fix_manifest_line_endings.py`（新） | 幂等重算清单；已是 LF 口径且无变化时不写回 |
| `a22_crlf_guard_test.py`（新） | 8 个用例锁住：LF 通过 / CRLF 归一化通过 / `--strict-lf` 拒绝 / 改内容失败 / 字节不符失败 / 缺标记失败 / a23 幂等 |

**验证**：

| 场景 | 结果 |
|---|---|
| 干净 LF 克隆（`git clone` + `core.autocrlf=false`，commit `89ddb29` + 本次补丁） | `a17` → `artifacts_checked=36`、`fail_count=0`、**rc=0**；`--strict-lf` 同样 rc=0 |
| Windows CRLF 工作树 | `a17` → 0 失败（归一化后），`files_with_crlf=36` 如实记录 |
| 36 个产物的**内容**（`git diff` 与 blob sha） | **完全未变**（`pools/ select3/ pool_quality/` 的 `git diff` 为空） |
| `order_fragile` 各维度数值 | 与修复前**逐项相同**（见回报中的对照表） |

**只需记住三句**：
1) 清单口径从 CRLF 改为 LF，`a17` 在干净检出上 `fail_count=0`；
2) **本轮修复只影响清单，不影响产物内容与任何检索数值**；
3) 协议串仍是 `a-side/retrieval-interface-v1`（未改 top-k / select-k / 排序键 / 归一化 / 种子）。
